# CLAUDE.md — MK Timekeeping & Compliance POC

FastAPI + SQLAlchemy + Jinja2 internal tool replacing three legacy spreadsheets for
time/leave/compliance tracking (~45 staff, originally all India-based offshore, now also
US-based). Spec: docs/PRD.md. Onboarding: HANDOFF.md.

## Commands

```bash
.venv/bin/python -m uvicorn app.main:app --port 8127     # run (http://localhost:8127, dev pick-a-user auth)
.venv/bin/python -m pytest tests/ -q                     # 382 tests — must stay green
.venv/bin/python -m legacy.verify_strikes                # acceptance: MUST print 168/168
rm tms.db && .venv/bin/python -m legacy.import_legacy    # rebuild DB from the 3 legacy .ods files
```

## Hard rules

- **The project directory name ends with a trailing space** — always quote absolute paths.
- Python 3.9 (system). No `X | Y` unions in runtime annotations; use `Optional[...]`.
- All durations/targets/variances are **integer minutes**; times-of-day are minutes since midnight. No floats. Format via Jinja filters `hm`/`hm_signed`/`clock`.
- **One fixed reference timezone, not per-employee ones** (manager request, 2026-08-10): every `start_minute`/`end_minute`/"today" the app captures from the real world is expressed in `app/util.py`'s `BUSINESS_TZ` (`America/Chicago`, handles CST/CDT automatically) — never the server container's own OS clock (Cloud Run defaults to UTC) and never wherever an employee physically is. Always capture "now"/"today" via `util.now_local()`/`util.today_local()` — never call `dt.datetime.now()`/`dt.date.today()` directly anywhere a clock-face value or business day is being determined. (`dt.datetime.utcnow()` is still correct and unchanged for audit-trail timestamps like `reviewed_at`/`updated_at`/`started_at` — those are pure elapsed-time/audit values, not clock-face-of-day, so they stay in UTC.)
- Every human-read date/timestamp is **MM/DD/YYYY** (manager request, 2026-08-03) via the `mdy`/`mdy_dt` Jinja filters or `app/util.py`'s `fmt_date`/`fmt_datetime` — never a raw `.isoformat()`/`.strftime()` in a template or export. Exception: `<input type="date">` values, hidden form fields, and option/checkbox submit values stay ISO (`YYYY-MM-DD`) — that's the HTML date-input spec and what `parse_date_field`/`dt.date.fromisoformat` expect back, not something a human reads.
- **Date *pickers* display mm/dd/yyyy too** (Ganesh, 2026-08-21) — `app/static/mdy_datepicker.js`, loaded once in `base.html`, progressively enhances every `<input type="date">` on every page automatically. Don't build a per-template date-picker or add a text-format hint another way — just use a plain `<input type="date">` like always; the script finds it. The native input stays in the DOM (hidden) and is still what actually submits, still holding the ISO value — the hard rule above is unchanged, this only touches what's displayed.
- `DayStatus.source='imported'` rows are **frozen legacy fact** — never recompute, migrate, or "fix" them (raw sheet cell is in `imported_token`). Admins change history via overrides only.
- `strike_exempt=True` rows (pre-policy days before 2026-04-15) must never count as strikes — the legacy sheets' own formulas excluded them. Changing this breaks `verify_strikes`.
- Status precedence: override → compensation (`comp_erases_strike` config) → base. Implemented in `DayStatus.effective_status()` and `engine.strikes_in()` — change both or neither.
- Any change to `app/engine.py`, `app/validation.py`, or `legacy/import_legacy.py` ⇒ run pytest **and** verify_strikes before calling it done.
- Schema changes: no alembic in the POC — `rm tms.db` + re-import is the migration path.
- Config lives in the `config` table (defaults: `CONFIG_DEFAULTS` in app/models.py); read via `engine.get_config(db)`, never hardcode thresholds.
- **Holidays are one shared company-wide list, not per-country** (manager request, 2026-08-14 — reverted a brief 2026-08-12 per-country split; holidays apply to every employee regardless of location). `engine.holidays_set(db, location=None)` always returns every Holiday row unscoped — `location` is accepted for backward compatibility but ignored, so it's fine (and preferred going forward) to just call `holidays_set(db)`. `Employee.location` and `Holiday.location` still exist as columns (see Holiday's docstring in app/models.py for why — dropping them isn't an additive schema change, and this app has real production data now) but nothing reads `Holiday.location` to filter anything anymore; new Holiday rows just get `DEFAULT_LOCATION` stamped on invisibly. Don't reintroduce per-employee holiday scoping without checking with Ganesh first — it was tried once and reverted within days.

Briefly defaulted off for the 2026-08-13 deploy so My Month's read-only lookback and a button-highlight fix could ship first; back to on the same day once that landed. - **Task Planning ("Plan for the Day" + Start/Pause/Resume/Stop, Ganesh, 2026-08-21) ships without a feature flag** — unlike Leave V2 above, it touches neither `app/engine.py` nor `app/validation.py`, so the pytest+verify_strikes hard rule two bullets up doesn't gate it. Why: every Start-to-Pause (or Start-to-Stop) segment becomes its OWN ordinary `TaskEntry` row through the exact same `_finish_task_timer()`/`validate_entry()` path the pre-existing Auto time capture timer already used — a paused-and-resumed plan just produces two normal rows with real clock times, not one row with an internal gap, so there was never a new overlap/cap/duration case for `validate_entry`/`compute_day` to learn. New tables/columns are additive-only: `PlannedTask` (`status`: `planned`/`running`/`paused`/`done`, see `m.PLAN_STATUSES`) and a nullable `ActiveTaskTimer.planned_task_id` — set only when the single shared active timer (same `UniqueConstraint("employee_id")` Auto time capture already enforces) was opened from a plan's Start/Resume rather than the ad-hoc timer form; NULL for every ad-hoc timer, unchanged. `app/routes/employee.py`'s `_stop_current_timer_if_any()` is what both `start_task_timer` and `/plan/{id}/start` now share for "starting one auto-finishes whatever else was running" — if the finished timer was plan-linked, that plan goes back to `paused` rather than being left stranded in `running`. Task log rows past the day's target get a distinct color via `util.overtime_row_flags()` — a pure, tested cumulative-sum helper, not compliance math (`DayStatus.target_minutes` is untouched). Plans are always "today" only, same live convention as Break/Punch/Auto time capture (`today.html` hides the whole section on any other day). **Admins see the same coloring** (Ganesh asked 2026-08-21) — `admin/person.html`'s Task log reuses `overtime_row_flags()` too, but driven by each day's already-computed `DayStatus.target_minutes` (set by `recompute_employee`, which this route already runs) rather than a fresh live leave/break calc, since it's rendering a whole month of past days, not just "today." - **Compensation links now allocate by the MINUTE, not the whole day (Ganesh, 2026-08-25)** — before this, linking consumed a surplus day's *entire* variance and blocked it from ever being reused, even if the shortfall only needed part of it, and a shortfall day could only ever be targeted by one link. Ganesh's own example: an 8-hour shortfall with a surplus day worth 10 hours should leave that day with 2 hours still available afterward; three 2-hour surplus days linked against an 8-hour shortfall should leave the shortfall at -2:00 (not silently treated as done, and not rejected outright) so a later link can finish it off. New nullable `CompensationLink.surplus_minutes` column (`app/models.py`, JSON `{"YYYY-MM-DD": minutes}` — how many minutes of each surplus day THIS link actually used, not just which days). Reading side lives in `app/engine.py`: `_link_allocated_minutes()` (one link's own total, with an old-format fallback — a pre-2026-08-25 link has no `surplus_minutes`, so it's read as having consumed each `surplus_dates` day in full, which is the correct frozen reading for it, not a gap to backfill), `shortfall_allocated_minutes()`/`shortfall_allocated_minutes_by_date()` (sum across every link that targets a given shortfall day — a day can now be covered by more than one partial link), `surplus_minutes_used_by_date()` (sum across every link for a given surplus day). Writing side: `allocate_surplus_minutes()` greedily consumes ticked surplus days oldest-first until the shortfall's remaining deficit is covered, skipping (not erroring on) a day with nothing left — shared by both `add_complink()` (admin-direct, `app/routes/admin.py`) and `request_compensation_match()` (employee self-service, `app/routes/employee.py`) so the two flows can't drift apart; `approve_complink()` doesn't need its own allocation step since the employee's request already computed and stored it at submission time. `evaluate_link()` was split into two related but distinct signals: `link.fully_compensated` (did THIS link alone cover the whole deficit — drives that link's own row badge and flash message) vs. `DayStatus.compensated` (the day's TRUE aggregate across every link targeting it — drives strike erasure via `comp_erases_strike`, and is what actually matters when a second link finishes off a day an earlier partial link started). `compensated_dates()` (read by `recompute_employee()` on every regular recompute pass — i.e. on most page loads) was rewritten the same way; missing this would have meant a day fully covered by two partial links got silently un-flagged the next time anyone loaded a page for that employee. The Shortfall day / Surplus day pickers on Person Detail, Overtime Management, and the employee-facing Overtime page all show remaining balances now (e.g. "2:00 remaining of 8:00 — partially linked") instead of a binary already-linked/not-linked state. No `verify_strikes` confirmation possible here either (same missing-legacy-bundle gap as Leave V2) — verified instead via a standalone Python simulation of the allocation algorithm (exact match on both of Ganesh's worked examples plus edge cases: exact-match, under-supply, a second link finishing a partial day, order-sensitive greedy allocation, skipping an exhausted day) and a real-SQLite integration check against hand-seeded `imported`-source test rows in `tms_demo.db` (Alok Gupta 08/06, Tanvi Banerjee 08/08) reproducing both examples' numbers exactly.
